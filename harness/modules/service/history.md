# 会话历史

## 职责与所有权

调用者通过应用服务模块的 Session 管理接口 查询历史与订阅事件；本文展开内部协作，不增加与应用服务模块并列的公共 module。[^direction]

会话历史是应用服务模块内部的提交职责，负责事实的持久提交协调、只读历史、实时分发和通用恢复校验；事件结构、时间与事件身份来源归 Runtime。它封装“完整事实何时成为可公开的历史”，使消费者无需解释存储提交过程。

Runtime adapter 决定一个原生观察如何转换为公共事实，并自行管理恢复所需私有证据。会话历史决定该公共事实是否满足通用合同及何时提交；它不解析原生坐标或私有证据版本。

文件提交与编码的待决事项见[持久化承载](../../bindings/storage.md)；本模块不绑定存储引擎。

## 完整事实与预览

完整条目来自真实 Agent 观察。预览用于显示生成中的内容，不因空闲、取消、失败、断线、归档或停止而自动补成完整历史。用户输入副本不能替代真实完整用户条目。

条目完成与前台工作结束分别表达。工具调用、执行结果和控制批准也分别表达；调用参数完整不证明已经执行。输出缺失、显式空值和已知截断保持区别。

MASS 不在内存跨事件保存或拼接 delta，只有 chunk 的 adapter 不自动得到完整消息历史。

持久事件种类由[运行时事件合同](../runtime/events.md)定义。完整观察并不意味着所有状态通知都必须持久化；预览与其他实时通知不进入历史，所有事件仍使用统一 eventId。

## 提交与发布

每个会话在任一时刻只有一个顺序提交责任：

1. 校验公共事实，并固定来源 Session 及其本次运行的内部证据关联。
2. 保留 Runtime adapter 提供的 time 与 eventId：time 优先取原始事件、缺失时生成；eventId 在创建统一事件时生成一次 UUID，同一事件重试保留原值。Service 与 HistoryStore 不重新分配。Service 串行协调同一 Session 的追加，保留源事件接纳顺序。
3. 通过 HistoryStore.append 直接保存 SessionEvent，允许同一 Session 的有序批量，完成规定的持久化屏障。
4. 向实时订阅和事件处理器发布同一不可变公共事件。

工具调用与结果可以属于同一条目，但各有独立 eventId；不能按 itemId 覆盖历史。不同会话独立推进。恢复保留事件 ID、已提交历史顺序和最后同步位置，不依赖连续计数器；恢复读取已存事件时保留其 UUID；当前不请求原生历史重放，也不承诺原生事件去重。

写入失败时不发布失败记录，并封闭该写入者的进一步持久提交。修复底层路径不自动重开写入；重新取得写入权必须遵守显式恢复和校验规则。失败诊断不能伪装成已提交事实。

持久化屏障的强度需要明确说明。刷新、掉电持久性、元信息原子保存和跨记录事务是不同保证，不能相互替代。尚未进入屏障的原生事实可能随故障丢失，不能宣告为已排空。

## 历史与实时观察

历史查询返回已提交公共事件，不返回私有证据，不激活 Runtime，也不调用业务处理器。读取验证持久身份、记录结构和顺序，不能用请求页之外的损坏记录隐藏错误。

实时观察与历史读取是 SessionService interface 中语义不同的会话操作。订阅只观察之后的事件，不自动补历史；取消订阅只结束观察，不取消 Agent 工作。读取与关闭接口见 [EventSubscription](observation.tsp)，HTTP 只映射这一行为。

实时订阅资源有界，慢订阅者可以断开；消费者过载不能迫使核心修改已提交事件。跨断线连续消费、持久消费游标和恰好一次业务处理都需要额外合同，不能从实时通知推断。

## 统一历史查询

SessionService.listHistoryEvents 与 HistoryStore.list 共用 [HistoryQuery、HistoryPage](../../shared/history-models.tsp)。Service 按名称或 ID 解析同一 sessionId 后传递查询，返回 events、next、syncedEventId，不再使用资源列表的 Page<T>/PageCursor。

query.types 为 OR 精确匹配，省略表示全部类型，空数组非法；实时类型没有持久记录可返回。先过滤再按持久追加顺序分页，after 是排他的 HistoryCursor，绑定 Session 与规范化过滤条件（类型集合忽略重复和次序），不绑定 limit。默认 limit=100，不设合同级最大值，实现容量不足时明确报错；next 仅在该页读取视图内存在后续匹配事件时返回。syncedEventId 来自同一读取视图的全会话同步进度，不因过滤改变。

每次调用读取自己的快照，不承诺跨页快照隔离；后续追加可在下一次读取出现。游标不能比较大小、与 eventId 互换或依赖易变的数据库行号；无效、过期或 Session/过滤条件不符时返回明确错误，不静默从头开始。游标编码与保留期限由 Store 实现定义；有效游标应在可重建索引重建后继续有效。

## HistoryStore 同步进度

HistoryStore 的完整接口见 [TypeSpec](../store/history-store.tsp)。getSyncProgress 返回最后持久同步且可读取的 syncedEventId，尚无历史时为 null；它不是 SQLite 内部索引状态，没有大小关系，不能计算同步差值或直接宣称追平上游。list 返回相同读取视图的 syncedEventId，并通过不透明 after/next 游标分页；查询过滤不改变全会话同步位置。

实时预览可以领先完整历史。完整持久事实仍遵守先提交再发布的顺序。读取可落后于调用方观察到的事件；判断目标事件是否已经同步需要核对其存在，不能比较 eventId 大小或从空页推断上游没有新事件。

append 支持非空批次；成功覆盖本批全部事件，失败不保证整批未写入。调用方核对进度与已有事件后，使用原 eventId 重试；旧事件重试不能使进度倒退。批次原子提交协议与准确幂等比较规则仍待定义。

## 校验与恢复协作

通用校验检查元信息、公共记录、会话归属、eventId 唯一性和持久读取顺序。私有绑定、原生来源与公共投影的一致性由对应 Runtime adapter 校验。

全部已提交公共事件及 Runtime 管理的私有证据分别通过验证后，才允许修复未提交尾部；HistoryStore 不承载私有证据。已提交记录损坏不能当成尾部修复，也不能先改写数据再报告错误。只读查询不修复文件。

恢复次序由应用服务模块按 [Session 管理](session.md)规则编排。历史提交职责 不主动启动 Agent，不选择替代实例，不把旧记录重新投递给业务消费者。

## 容量与停止

完整持久事实在有界资源内等待或明确失败，不能静默丢失；预览允许按策略丢弃。持续压力可能传回共享运行连接，容量限制不等于整个进程内存上限。

停止区分已接纳到提交核心的事实和仍在上游的观察。只对前者承诺在声明条件下排空；永久阻塞存储时不能同时承诺有限时间完成与全部成功提交。

## 验收场景

| 场景 | 应观察到的行为 |
|---|---|
| 只有增量，随后连接退出 | 无伪造的完整历史条目 |
| 持久化写入失败 | SSE 与处理器均收不到失败记录的已提交版本 |
| 同一工具调用及结果 | itemId 一致，eventId 各自独立 |
| 慢订阅者 | 按有限策略断开，健康提交继续 |
| 恢复时私有证据不一致 | 在修尾或激活前失败，保留原数据 |
| 历史查询与恢复 | 查询不运行消费者，恢复不重演旧业务动作 |

## 待决事项

事件结构见[SessionEvent](../runtime/session-events.tsp)；持久化屏障强度与准确文件格式仍待确认。HistoryStore 的 syncedEventId 仅是最后同步事件身份，不等同于业务消费者进度；具体数据库投影机制、持久消费者进度和历史导入仍待设计。历史查询与分页已有当前合同，具体实现与验收另行验证。

[^direction]: 当前讨论确定 Service 依赖 Store 持久化资源、依赖 Runtime 执行运行操作；HTTP 只做协议映射，具体接口由负责人定义。

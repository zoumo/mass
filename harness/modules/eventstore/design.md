# EventStore 模块设计

EventStore 是独立模块，取代原 HistoryStore 名称，由 Service 直接调用追加和历史查询；接口、文件、SQL 连接、打开、关闭和恢复单独管理。它不读取 MetaStore，不修改资源状态，不启动 Runtime，不发布实时事件，也不运行事件处理器。[^split-direction]

## 权威、输入与职责

Agent 观察由 Runtime adapter 转换为统一 SessionEvent。Service 核对已有运行绑定与 Session 身份，按 Session 有序提交。EventStore 以稳定 sessionId 寻址并校验输入事件和该日志绑定；绑定所需身份随事件日志保存，不能依靠元数据 SQL 才能重建事件 SQL。

文件保存全部已提交持久事件及解释顺序、身份、游标所需材料，是唯一真相源。events.jsonl 仅追加新事件；恢复意图只含本次增量和必要边界证据，不保存全量历史。SQLite 保存完整事件的派生查询副本及内部文件消费位置，全部可由事件文件恢复；SQL 独有行不能反向成为事实。

仅接收当前事件合同允许的五种持久类型；chunk、临时通知和 Driver 私有恢复材料不进入公共历史。不得跨事件拼接预览制造完整历史，不常驻全量事件正文或身份/位置索引。

## 追加、查询与同步进度

EventStore 提供 append(sessionId, events[])、list(sessionId, query) 和 getSyncProgress(sessionId)，按全局 sessionId 寻址。append 直接支持批量，单条写入使用长度为 1 的批次；同一批次不得混入其他 Session 的记录。

EventStore 直接保存 SessionEvent，不增加历史记录包装或私有证据字段。eventId 由 Runtime adapter 在创建统一事件时生成一次 UUID；Store 不重写 eventId/time。同一 sessionId/eventId 的相同事件可幂等重试，不重复追加、不改变原位置；同一 ID 对应不同内容则报错。事件 ID 仅用于唯一标识，不承担排序、计数或分页职责。不同 UUID 即使原生 ID 或内容相同，也不合并；同一 UUID 的写入幂等不等于原生事实去重，后者当前不提供。准确事件等价比较仍需细化，恢复私有材料由 Runtime 管理。

历史按持久追加顺序读取，批内按输入顺序追加；Service 串行协调同一 Session 的追加，使输入保持源事件顺序。Store 不能通过 eventId 大小或时间推断事件缺口，也不承诺自动重排迟到事件。

getSyncProgress 返回 syncedEventId，即最后同步、持久保存且可读取的事件身份，尚无事件时为 null；不是 SQLite 内部索引进度。旧事件重试不改变进度；ID 无大小关系，不能计算剩余数量，也不能据此宣称追平上游。

append 成功表示本批全部事件已经可持久读取，返回当前 syncedEventId；不承诺调用时长或整批事务。失败或结果未知时不能假定整批未写入；调用方保留原事件和 eventId，重试仍使用相同 ID。同步位置、校验与续接由 EventStore 隐藏，调用方无需先执行恢复操作或重新打开 Store。文件层批次提交边界、持久化屏障和故障恢复协议仍待设计。

list 返回 SessionEvent、可选 next 游标和与本次读取视图一致的 syncedEventId。query.after 接受上页 next，调用方不得解析、自造或用 eventId 代替游标；游标绑定 Session 与过滤条件，不匹配或无效时明确报错。query.types 按事件 type 精确过滤，多类型为 OR，省略表示全部类型，不接受空数组。先筛选再按 limit 分页，next 仅在存在后续匹配事件时提供；过滤不改变全会话同步进度。空页不表示已追平上游。

文件保存稳定读取顺序和恢复所需信息。SQLite 重建不能改变已有事件身份、历史顺序或同步位置；有效游标的解释不能仅依赖重建会变化的数据库行号。游标具体编码、生命周期和过期规则仍待定义。EventStore 不发布实时事件，不运行消费者，也不激活 Runtime。

## 文件提交、SQL 投影与发布顺序

正常追加顺序固定为：验证输入与幂等性 → 持久追加文件 → SQL 事务写入完整事件并推进内部文件消费位置 → append 返回成功。SQL 事件与内部消费位置在同一个事务中提交；公开 syncedEventId 仍是最后持久且可查询的事件身份，不是内部文件位置。

Service 直接调用 append，成功后才调用 Session Broadcast.publish；Broadcast 不调用 EventStore，不管理历史或处理链。同一 Session 的后续持久事件不得越过未完成的前序事件；不同 Session 不承诺全局顺序。文件已经提交但 SQL 尚未消费，表示事实已保存而查询副本落后，不是文件提交被撤销。

文件成功、SQL 失败时返回明确的未知结果或副本未就绪错误，保留文件与恢复证据，不发布该次持久事件。后续追加不得越过未结算前缀，查询不得静默漏项。正常追加自动驱动 SQL 投影；失败后，后续同步触发由 EventStore 自动从已确认且验证通过的消费位置继续，无需 Service 调用恢复 Interface 或重新打开 Store。同步仍失败时保留原已确认位置，明确返回错误；下一次触发继续尝试，不把失败当作已同步。原 ID 重试必须对照已提交文件事实去重，不可仅凭落后的 SQL 判定事件不存在。MetaStore 不因这一故障被重建或切换后端；Service 按受影响操作决定是否拒绝请求，不保证所有业务仍可用。

文件追加本身的半写、持久屏障、原前缀校验与幂等恢复仍由 EventStore 承担，不能用 SQL 事务替代。分歧尾部或已提交记录损坏明确失败并保留证据，不擅自截断旧历史。SQL 成功但响应未知时，原 ID 重试不重复追加。

## 打开、重建与只读

打开时先校验事件文件和未完成追加，再以有界流式批次同步 SQL 副本；在受影响历史具备一致查询视图前不宣告 EventStore 就绪。有效 SQL 副本保留已确认消费位置，后续同步只追加该位置之后已验证的文件尾部，不因一次同步失败而从头处理全部历史。消费位置及其对应文件前缀必须校验，不能跳过记录或接纳 SQL 独有事实；SQL 事件与位置原子提交，事务失败不推进位置。副本缺失或损坏而无法使用原位置时，从权威文件重建，不把坏位置当作可信起点。准确增量校验协议仍需细化。

自动同步只修复查询副本，不重写已提交权威事实、不重新发布事件或运行 Handler，也不代替下文尚待裁决的物理修尾前置验证。除正常追加驱动投影外，其他触发时机及查询是等待同步还是明确返回副本未就绪仍待细化；这些调度选择不增加调用方必须执行的恢复协议。

删除、损坏或重建事件 SQL 不影响元数据和事件文件；事件重建不要求 MetaStore 可用，也不能重新生成资源。查询、投影重建和进度恢复不激活 Agent，不重新投递历史给业务处理器。

只读打开不修复权威文件或写入持久副本；需要时使用自有临时磁盘副本并清理。内存仅保留当前批次、结果页、紧凑检查点和有界数据库页缓存。

## 模块边界、待决事项与验收

元数据及其权威后端见 [MetaStore](../metastore/design.md)，跨模块业务协调由 Service 负责；实时分发归 [Events](../events/design.md)，历史提交和失败结算归 Service，EventStore 不调用 Events。不存在元数据与事件的共同提交意图或跨库原子事务。Session 删除后的日志保留/清理政策另行明确，不能由外键或元数据 SQL 更新隐式决定。

此前 review 指出的“独立物理修尾是否需要 Driver 私有证据先行验证”尚未裁决；EventStore 的独立恢复目标与现有恢复前置规则必须在相关修尾实现前协调，不因本次 Events 拆分视为已解决。

具体文件布局、刷新与掉电保证、准确提交边界、事件等价比较、增量校验与恢复调度仍需在 [持久化承载](../../bindings/storage.md)下细化。实时订阅 是实时通知；SQL 提交和网络送达不原子，不新增可靠投递或业务重放保证。

验收覆盖追加、原 ID 幂等、冲突、半写、文件成功但 SQL 失败后自动续同步、SQL 事件与消费位置原子提交、有效位置续接而非全量重建、副本缺失/损坏重建、分页/进度/游标稳定、同名身份隔离、有界内存以及发布顺序。同步失败后再次触发须处理未同步尾部且不重复记录、不跳过事实、不补广播；位置或前缀校验失败须保留证据。

[^split-direction]: 当前人类请求明确保留 EventStore 文件权威与 SQL 可重建，并要求模块及接口独立。

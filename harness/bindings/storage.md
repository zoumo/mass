# 持久化承载

## 权威数据与职责

文件系统保存完整持久数据；SQLite 可选，仅作可重建索引和查询加速层。无数据库时也必须能够恢复资源、名称归属、版本、事件身份、历史顺序和同步位置。具体接口见 [MetaStore](../modules/store/meta-store.tsp) 与 [HistoryStore](../modules/store/history-store.tsp)。

MetaStore 保存 Runtime、Session 的完整资源。Session.spec.runtimeRef 保存 Runtime 名称；持久归属不使用或比较 Runtime uid。metadata.uid 仍保存资源自身标识，不承担跨资源归属校验。generation、resourceVersion、createdAt 与 sessionId 在索引重建时原样恢复。

HistoryStore 直接保存统一 SessionEvent，不增加记录/证据包装。保留 adapter 生成的 eventId、time、完整名称和 payload，按持久追加顺序读取；不使用 eventId 大小或连续序号推断顺序。允许同一事件的写入幂等重试，不承诺整批事务。

RuntimeDriver 自行管理和持久保存私有恢复材料。Store 不解释原生证据，公共事件和查询不暴露私有恢复材料；公共历史校验与原生恢复校验的协作见[会话历史](../modules/service/history.md)。

## 文件一致性要求

- 文件包含恢复完整状态所需的数据，不允许数据库成为任何权威字段的唯一副本。
- 元信息持久提交成功前不公开 Session 创建成功；完整事实提交成功前不向观察者发布。
- 名称和原生 ID 不直接决定用户可控路径，存储定位与布局由 Store 隐藏。
- 同一数据目录必须具有明确的排他写入所有者；读取、重建与写入的并发规则由文件协议定义。
- 同名 Runtime 的资源 uid 变化不影响 Session 名称归属；原生恢复是否可行仍由 Driver 验证。
- 只读查询不修复文件。已提交记录损坏必须明确失败；修复未提交尾部前，先完成公共历史与原生恢复材料校验。
- 事件、资源及动态值编码失败必须明确报错，不能静默丢字段或篡改原事件身份。
- 不提供兼容层、隐式格式转换或自动迁移；不支持的数据格式明确拒绝并保留。

## 待定义的文件协议

1. 文件布局、资源/历史格式版本及编码规则。
2. 创建、全量更新和删除的提交点、原子性与并发冲突处理。
3. 刷新、掉电持久性与跨文件一致性的准确保证。
4. 批次部分写入的可见范围、幂等比较及故障恢复。
5. 已提交与未提交尾部的判定、允许修复的条件与流程。
6. 索引修复、重建期间的查询策略、有效游标保持与过期规则。
7. 私有恢复格式的验证入口及跨语言读写与冷恢复的验收范围。

这些事项尚未定稿；本页不预设具体目录、文件名、换行提交方式、数据库表或私有证据版本。

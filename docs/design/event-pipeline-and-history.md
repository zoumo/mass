# 当前事件提交与历史架构

本文描述当前已实现的文件历史和处理器合同；数据库查询投影、分页与同步仍未交付。

## 完整事实与预览

只有适配方提供的完整消息、思考、工具调用和工具结果进入历史。条目完成不等于整个前台工作结束。预览用于实时显示，不累积成完整内容，不在空闲、取消、失败、断线、归档或停止时补写。

用户消息来自真实完整回显，不能用本地输入副本替代。输入回执不是完整事件、模型消费证明或 Journal 提交证明。工具结果保持上游证据能说明的状态和输出完整性，缺失、空与截断分别表达。

## 固定提交次序

适配交付归一化事实。会话提交核心按顺序处理，分配下一 seq 和时间，将 schemaVersion=2 公共事件与适配方版本化私有证据写入同一换行记录并刷新，然后把同一不可变事件发布给 SSE 与处理器。处理器不能改写、过滤或重排提交核心已接纳的持久事实。

实时预览不进入 Journal，也没有持久 seq。预览丢弃不影响完整内容。内部生命周期观察不因实时订阅者丢消息而被忽略。

同一会话只有一个顺序写入责任，工具调用和结果可共享 itemId，但各占独立 seq，不按 itemId 覆盖历史。不同会话可独立推进。写入失败封闭该写入者，不发布失败记录；修好路径不自动恢复写入。

当前刷新强度不承诺每条记录都具备掉电不丢保证。元信息原子替换和 Journal 追加不组成跨文件事务，具体存储边界见[存储合同](../storage.md)。

## 消费与过载

实时订阅与处理器各有有限容量。慢 SSE 订阅者被断开。每个会话与处理器组合按顺序执行，健康组合互不等待；处理器错误或过载只影响相应组合。具体停用、排空和关闭规则见[处理器合同](../handlers.md)。

已提交通知只是可丢的唤醒，不是持久消费进度。将来需要可靠业务动作或投影时，必须另有持久进度和幂等合同；当前未实现查询投影，也没有默认业务动作。

完整事实在有限队列中等待而非静默丢弃。持续积压可以反压到共享原生连接，影响其他会话和控制响应。有限内存不能同时保证无限生产与永久停止消费下的持续进展。容量及归一化失败的归属见[原生适配](native-runtime-connectors.md#native-ticket-06-bounded-core-delivery-and-shared-transport-pressure)。

## 恢复与观察

查询只读取文件，不激活 Agent 或调用处理器。严格恢复验证全部已提交记录和绑定后才修未提交尾部，继续公共序号，不重放旧输入或处理器动作。实时 SSE 只提供订阅后的事件，不补历史，也不承诺跨连接恰好一次。

公共字段见[事件 wire 合同](../events.md)。原生坐标、对象和一致性规则仅在适配方解释；通用 Runtime/提交核心只保存不透明证据，HTTP、SSE 和 Handler 仅消费公共事件。没有旧格式解码、双写或迁移。

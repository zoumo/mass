# 事件处理器

## 职责与规则来源

事件处理器是业务消费扩展，应用服务模块 负责其交付和生命周期；业务通过 Session 使用运行能力。本文不增加与应用服务模块并列的公共控制 module。[^direction]

应用服务模块 内部的事件处理职责管理事件消费者的构造、顺序交付、失败和关闭。它让业务动作具有明确的消费生命周期，而不参与事实提交或原生命令结算。

公共事件不可变，命令保持原目标，业务动作不阻塞原生控制。采用 agentrun 当前按 Session 构造 Sink、处理与关闭的基本形态，定义本模块的语言无关合同。持久历史提交与状态投影属于核心路径，不作为可选业务处理器；不照搬 MustSucceed 或同步逐个回调阻塞整个广播的实现。

## interface 与所有权

准确声明见 [event-handlers.tsp](event-handlers.tsp)，这是受信任的进程内扩展入口，不新增 HTTP 方法。

EventHandlerService.register 登记名称、声明式过滤、动态配置及 EventHandlerFactory。名称唯一，对现有持久 Session 和后续创建的 Session 生效；登记完成不意味着每个关系构造成功，失败记诊断并停用该关系，其他关系继续。factory.create 接收只读 Session 快照与配置，返回处理器、明确错误或 void（不适用）。构造必须位于有界执行资源内，不占用核心提交临界区。

处理器声明消费全部事件、已提交事件或指定公共类型。选择发生在交付前，不允许业务回调过滤、重排或改写提交核心已接纳的持久事实。

EventHandler.handle 接收不可变 SessionEvent、committed 标志与本次回调专属 EventHandlerCommands。来源上下文在内部识别Runtime 名称归属、Session、原运行和相关工作；Service 用它验证事件触发的操作是否仍然有效。业务无需管理额外运行凭据，也不能仅凭 sessionId 绕过来源验证。持久类型只在提交成功后交付一次（committed=true），实时类型在实时路径交付（committed=false），不先发未提交版本再重复通知提交版本。

业务可以更新自己的状态或构造副本，但不能更改原事件身份、时间和内容，也不能绕过核心提交发布历史。公开事件不携带 adapter 的私有证据。

只消费已提交事件的消费者，仅接收完成持久化屏障后的通知。收到通知不等于业务动作成功；可靠同步需要另行定义持久进度、补读和幂等合同。

## 顺序与生命周期

消费关系按 Runtime 名称、sessionId 和处理器登记共同区分。全局重复 sessionId 的第二次登记必须先被拒绝，不因此建立第二份消费关系；队列与命令仍校验 Runtime 名称、原 Driver 与原运行，不能只凭 ID 重绑。

同一消费关系一次处理一个事件，实时通知保持交付顺序，但不因统一 eventId 就进入持久历史。不同关系独立推进，登记顺序不决定动作完成顺序。有业务依赖的动作应由相应业务流程编排。

归档和断线保留非运行资源消费者。恢复同一 Session 延续已有消费顺序，不重新构造已存在的消费者，也不另开通道绕过旧队列。Runtime 始终保留已排队事件的原来源关联。

创建尚未完成时，消费者属于临时资源。创建失败要取消其待处理动作，并在期限内尝试关闭；只有持久身份与连接安装成功，才接受该 Session 的正式消费关系。历史查询和恢复验证均不投递旧历史。

## 过载与失败

交付资源有界，提交核心不等待业务回调完成，不为每个事件无限生成并行工作。

| 情况 | 消费策略 |
|---|---|
| 队列过载 | 停用该消费关系；排空已接纳交付后尝试关闭 |
| 回调失败或未处理异常 | 停用该消费关系；丢弃尚未处理交付并尝试关闭 |
| 构造或关闭失败 | 记录诊断，限制影响范围 |
| 已停用关系再次恢复 Session | 不因恢复而自动启用；只通过显式 enable 重新构造 |

上述失败不改变已提交历史，也不阻止健康消费者。诊断不得递归制造新的会话事件。

处理器属于受信任的进程内扩展。业务网络等待和命令调用不能占用提交或生命周期的临界区；永久阻塞或不协作的代码无法获得有限关闭保证。具体执行机制由各语言 implementation 自行选择。

## 命令与停止

处理器通过应用服务模块的 Session 管理接口 提交输入、取消或其他已声明能力。参数校验、准入与失败语义与外部调用一致；应用服务模块 拒绝旧运行上下文对新工作的控制，不因旧事件动作隐式恢复 Session。EventHandlerCommands 封装来源关联，只暴露 sendPrompt、answerInteraction 和 cancel；不提供隐式恢复或关闭当前回调所属关系的方法。cancel 固定原事件关联的工作，不能在回调执行时改选“最新工作”；缺少合法工作关联则拒绝，不能猜测。回调返回后 commands 失效，已接纳操作继续由原操作结算。

处理器触发的新事件仍通过正常提交与消费路径。业务负责防止自身无限动作循环，不能让事件核心替它判断业务终止。

系统停止按[总体架构](../../architecture.md)结束接纳、排空核心事实并释放运行资源，再在总消费者期限内排空和关闭。超过期限的交付可以终止，但不能声称关闭动作成功。普通消费队列不提供崩溃后业务动作恢复或恰好一次保证。

## 验收场景

| 场景 | 应观察到的行为 |
|---|---|
| 处理器修改自己的事件副本 | 其他消费者及历史中的事件保持原值 |
| 两实例返回相同 sessionId | 拒绝第二次 Session 登记，不创建冲突消费关系 |
| 单个处理器过载或失败 | 其他消费者和历史提交不受其业务错误影响 |
| 归档后恢复，有旧事件仍在队列 | 原消费顺序保持；旧事件的控制命令不影响恢复后的新工作 |
| 原生打开或持久化失败 | 临时消费者被结算，不依赖下一次请求清理 |
| 关闭期限到达 | 准确报告未完成关闭，不伪造业务成功 |

## 停用与重新启用

EventHandlerService.disable 停止该 Session 的新交付，排空并关闭实例；unregister 对该登记全部关系执行同样流程，确认全部完成后才移除登记。关闭超时或失败不得宣称释放成功，同名登记或 enable 不能覆盖仍未关闭的旧实例。回调失败按上表丢弃尚未处理交付，过载按上表排空已接纳交付。

显式 enable 在旧实例已关闭后重新调用 factory，不回放历史、不重试原失败动作、不启动或恢复 Agent；健康关系重复 enable 为幂等。归档后恢复 Session 不自动启用失败关系，也不重建健康关系。登记与停用状态当前为进程内状态，不承诺跨进程重启持久保存；进程重启由组装层重新登记，不补旧业务动作。

## 待决事项

可靠消费、持久消费进度、跨崩溃恢复和恰好一次业务动作不在当前处理器合同内。具体队列容量、执行期限及诊断输出由组装配置与语言实现给出，不宣称当前已有运行验证。本次不新增动态插件、远程处理器登记、默认业务动作或数据库投影。

[^direction]: 当前讨论确定 Service 依赖 Store 持久化资源、依赖 Runtime 执行运行操作；HTTP 只做协议映射，具体接口由负责人定义。
